# 文本聊天真机内存基线

**状态：待真机执行。** 本页为历史分页的验收步骤，不是测量报告。先测手头内存最紧张的表，再分别记录 Xiaomi Watch S3 / S4 / S4 Sport（圆屏包）和 REDMI Watch 5（方屏包）；一款通过不能替代其他型号。不要为测量在正式包中常驻采样或打开图片预览。

## 准备测试房间

1. 在测试 Nextcloud 实例新建专用空房间 A，并新建房间 B 用来验证切换。A 中加入两个测试账号：手表用一个，桌面端造数据及补发消息用另一个。不使用生产群聊。用 `npm run build:circle` 或 `npm run build:rect` 生成对应调试包，记录 Git 提交及包版本。
2. 在桌面上用 Node.js 18+ 生成 72 条编号消息，每 6 条插入一条长正文。把下面的地址、房间令牌（Talk 房间 URL 的最后一段）和账号换成测试值。在 Bash 中输入专用应用密码，不把它放入命令行参数。脚本仅向指定 HTTPS 地址发送，拒绝重定向，遇到错误立即停止；若只写入部分消息，请先检查房间，再换空房重跑，避免重复样本。

   ```bash
   read -rsp '测试应用密码: ' WATCH_TEST_PASSWORD; printf '\n'
   printf '%s\n' "$WATCH_TEST_PASSWORD" | node scripts/seed-watch-chat.mjs \
     'https://cloud.example.com' 'roomToken' 'fixture-user'
   unset WATCH_TEST_PASSWORD
   ```

3. 手表登录后确认能进 A/B。在同一轮比较中固定亮屏、网络和轮询间隔，保持同一 RPK 和账号；记录设备固件、Nextcloud/Talk 版本、轮询间隔、网络方式、测量工具及其覆盖范围。如果工具只能观察 JS 堆，不得把它写成整页或原生内存。没有可用指标时，在结果栏明确标记「未测」。

## 操作与判定

| 场景 | 操作 | 应观察到 |
| --- | --- | --- |
| 进房与翻页 | 冷启动进 A，记录进房后稳定值；连续点击「加载更早消息」直到无旧页 | 最新一批在最前，编号向下递减，无重复或跳号；超过两页后始终最多 24 条，翻到历史尽头也不继续堆积。样本长消息显示省略号，看不到末尾 `END-OF-LONG-TEXT`。 |
| 浏览期间来信 | 浏览历史时从桌面端发 `live-1`；等至少两个轮询间隔，再点「返回最新」 | 历史不被来信刷新；返回后滚到顶部、显示 `live-1`；随后发 `live-2` 验证轮询恢复且不重复。 |
| 写入与生命周期 | 发送一条手表消息，随后锁屏/切后台、回来，并在 A/B 间切换；另做一次离开时恰有读取尚未完成的测试 | 不重复显示刚发送的消息，旧房消息不串入新房，聊天页退后台不启动新轮询，返回后继续更新。若能看请求日志，区分离开前已发出的响应与离开后新发的请求。 |
| 引用回复 | 长按可回复消息，点「回复」并输入；先取消一次引用，再选旧消息发送；在桌面端确认引用目标。另用断网验证失败后恢复 | 保留单行摘要，× 只取消引用不丢草稿；成功可在桌面端识别为回复，失败保留引用和草稿、不自动重发。 |
| 表情反应 | 在普通消息上长按 →「表情」，添加并撤销 👍、❤️、😂；再用桌面端给窗口内消息添加或撤销，等一个轮询周期 | 表情字形可读、操作不遮挡；计数双向同步，撤销只影响自己；不出现额外系统消息，窗口仍最多 24 条。 |
| 长时压力 | 先跑 3 轮预热，再跑 20 轮：每轮进 A、翻至少 3 页、返回最新、切 B 再返回会话列表。每 5 轮补测一次键盘与前后台 | 记录各轮峰值和退回列表 30 秒后的值，观察是否持续抬升，同时记录卡顿、崩溃、被系统回收和恢复异常。 |
